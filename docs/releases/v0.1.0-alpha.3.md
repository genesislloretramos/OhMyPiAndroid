# v0.1.0-alpha.3

**alpha.2 installed on a real Android 14 phone and did not open.** It shipped with a green suite
of 917 JVM tests — 814 in `:core` and 103 in `:app`, zero failures — and a build that reproduced
byte for byte, and the app died about fifty milliseconds after the tap. That is the honest account
of what shipped, and it is the first thing in this document because a reader deciding whether to
trust a prerelease deserves to know that **a green JVM suite did not mean the app launched.**

Four independent process deaths on the launch path were found by a read-only audit and are fixed
here. None of them was a missing assertion in an obvious place; the interesting one is why a test
in the obvious place could not have caught it, and that is the last section.

## What is new since alpha.2

**Four launch crashes, and the guards put around them.**

1. **`FOREGROUND_SERVICE_SPECIAL_USE` was missing from the manifest — this is the crash that
   shipped.** Android 14 checks one permission per foreground-service *type* in addition to the
   general `FOREGROUND_SERVICE`. `ChatService.onCreate` called
   `startForeground(FOREGROUND_SERVICE_TYPE_SPECIAL_USE)`, the platform threw `SecurityException`,
   and an uncaught throw inside `Service.onCreate` killed the process about fifty milliseconds
   after the tap. The general permission was present; the per-type one was not, and the general
   one is not what Android 14 looks at.
2. **The published URL lost its scheme, on every device and every Android version.**
   `UiOrigins.kt` built the base with `substringAfter("://", "")`, which yields `127.0.0.1:8731`,
   and `HttpLoopback`'s own validator rejected that with `IllegalArgumentException` — uncaught on
   a main-thread `Handler` Runnable, so a second process death one to three seconds in.
   **Fixing only the permission would have turned a crash at fifty milliseconds into a crash at
   one to three seconds and cost a second round trip for the person testing it.** The base is now
   parsed as a whole, a base that will not validate becomes a null the caller carries on from,
   and the step is one pure function the tests can reach.
3. **The provisioning watcher thread had a `try` around `Thread.sleep` alone**, with the reader
   and the publisher outside it, and `:app` installed no uncaught-exception handler anywhere. The
   watcher is now a class of its own with the whole body covered, and `:app` has a handler that
   names the thread instead of letting the process disappear.
4. **The guest start ran unwrapped on a daemon thread**, while `GuestStart.kt`'s own KDoc claimed
   it "never throws". It now catches `Throwable` at the thread boundary and turns a throw into a
   named state, `START_FAILED`, which `omp doctor` prints with the reason. The KDoc's claim was
   part of the defect as much as the missing catch was.

**The guest's own LAMP install, from alpha.2, is unchanged and still in this artifact.** The
Debian still installs its own Apache, PHP and MariaDB with `apt` after the port bind check and
before Apache, bounded at five minutes, resumed rather than re-derived, recorded before the first
step, with `LAMP_MISSING`, `LAMP_INSTALLING` and `LAMP_FAILED` among the nine named states — and
all nine of those states still refuse the guest's origin rather than substituting this app's own
server. `omp doctor`'s `guest origin` section still prints the `packages:` line putting what
`dpkg` reports is on the disk beside what the manifest estimated. What has changed is that none of
it has ever been reached on a phone, because the app died before it could be.

**A tenth state, `START_FAILED`, joins them.** It is what a throw at the thread boundary now
becomes instead of a process death, and `omp doctor` prints it with the reason. The state is
non-serving, like the others that are not serving, so a guest that throws on the way up is
reported rather than shown.

## What prevents a fifth crash of the same kind

Not more tests in general — a test placed where the old one already was would not have caught
any of these.

**`MergedManifestTest` reads the *merged* manifest, not the source one.** The obvious place to
check a permission is `app/src/main/AndroidManifest.xml`, and there is already a test there
(`ChatServiceManifestTest`). It would have stayed green through the bug that shipped, because
**the device never reads that file.** AGP merges the app manifest with every library's into
`build/intermediates/merged_manifests/debug/processDebugManifest/AndroidManifest.xml`, and *that*
is what is packaged into the APK and read by the package manager. A check against the source
manifest is a check that the line is still typed somewhere it happens to be, and not a check that
the line survived. The new test parses the merged file, which is the one a device reads, and
holds the service type, the permission and the `startForeground` call to the same value — because a
mismatch between them kills the app on launch with a stack trace about a type.

**The other three guards are placed at the boundary, not at the call site.** A parse that can
refuse is caught where it is parsed and becomes a null, because a phone that dies on launch over a
value on the disk is worse than a screen that says it is still waiting. A thread that can throw is
wrapped where the thread is started, because a throw there is a process death and the same
statement anywhere else is a test assertion. `:app` now has an uncaught-exception handler that
names the thread, because the alternative is a process that disappears with nothing in any log
but a line number.

**None of that is a claim that the next launch is safe.** It is a claim about four specific
defects and about the class of mistake that had no guard. A fifth defect of a shape nobody has
thought of yet is not addressed by any of this, and the honest position on the whole release is
the one below.

## What it is

A terminal emulator for Android, written in Kotlin, where the shell is the product: the lexer,
parser, expander, line editor and the terminal emulator itself are all code in this repository,
and none of them is a binary, a native library or a `Runtime.exec`. `ls`, `cat`, `grep`, `find`,
`sed`, `du`, `tree`, `zip`, `sort`, `df`, `uname`, `getprop`, `pm`, `am`, `dumpsys`, `settings`,
`wm`, `screencap` and `curl` are Kotlin running inside the app's own sandbox. Where Android
refuses an ordinary app something — `chmod`, `mount -o`, `dmesg`, `logcat`, `netstat`, `su`,
`sudo` — the shell says why instead of pretending.

There are two more things inside it:

- **An in-process userspace VM** (`vm`) — Ubuntu Server 24.04.1 LTS on a directory in the app's
  own storage. One process, no hypervisor, no image to download, and `root` inside it is a name
  the VM kernel answers to, not a privilege on the phone. It has `apt`, `dpkg`, `systemctl` and
  `journalctl`, which the phone shell deliberately does not, and `/mnt/omp` is a real bind onto
  `Documents/omp`.
- **A real Debian guest** (`omp provision`) — downloaded and unpacked on the phone, carrying the
  real upstream `omp` on the two ABIs it is built for, with Apache, PHP and MariaDB around it, and
  its own chat page served by that Apache.

And one agent in two places: the Kotlin one in this build, which reaches one conversation folder
with five file tools, and the upstream one inside the Debian.

## What it does

- A working shell: pipelines, job control (`&`, `jobs`, `wait`, `kill`), redirections,
  substitutions, globbing, quoting, history, and around ninety builtins. A pipeline answers with
  its **last** stage's status, `jobs` and `kill` answer only for what is running, and `wait` is the
  command that answers for a job that has already finished.
- A line editor with a modifier bar — CTRL, ALT, ESC, TAB, arrows, HOME/END, PGUP/PGDN — so
  Ctrl-C and Ctrl-L work without a hardware keyboard. Long-press to select, pinch to resize, Back
  to stop.
- `omp new photos` makes `Documents/omp/photos`, enters it, and puts its two spellings in the
  environment. Inside a conversation, `omp` is not the launcher any more — it is the coding
  agent. It reads and writes inside that one folder, and **every write is put to you first** — the
  path, the size, and for an edit the old and the new text — with `omp --yes` as the one thing
  that skips the question, recorded as `auto` rather than `y`.
- `omp provision` downloads a Debian rootfs and an agent binary, prices them from its own
  manifest, asks, and **moves nothing without a `y` given in that run**. It can be cancelled with
  Ctrl-C and resumed, because the `.part` file's own length is the offset the next run asks for.
- The guest is started at every start of the app: a port is reserved, the guest's own LAMP is
  installed with `apt`, the API configuration is linked into Apache, Apache is started in the
  foreground, a page is asked for, the boot's `omp update` runs, and which of **ten** named states
  that was is written down. A `LAMP_MISSING`, `LAMP_INSTALLING`, `LAMP_FAILED`, `START_FAILED`,
  `PORT_TAKEN` or `APACHE_NOT_ANSWERING` shows this app's own server and **names it as this app's
  own server** rather than quietly handing over a chat from a different program. None of them
  serves, and none of them substitutes anything silently.
- A second door into the same agent: a foreground service puts a small HTTP server on
  `127.0.0.1:8731` — 8731 is what it asks for, and it takes an ephemeral port rather than failing
  if that one is gone — and puts the address on a notification, token and all. A browser on the
  phone gets the same conversations, the same five tools and the same write approval. `web`
  prints it; `web stop` ends it.
- `omp doctor` prints ten sections — `identity`, `guest`, `helper`, `provisioning`, `guest state`,
  `agent update`, `guest origin`, `chat`, `gaps`, `next` — one `key: value` per line, in a fixed
  order, read-only, so two runs can be diffed and one can be pasted into a bug report whole.

## How to install it

This is a sideloaded developer tool. It is not a Play Store app and it is not meant to be one:
all-files access and package visibility are both restricted by Play policy. **It is not signed for
distribution** — there is no release signing config in the tree, so the APK is debug-signed and
Android may warn you about it. That is expected.

The APK is attached to this release. Download it, or build it yourself:

```bash
export ANDROID_HOME="$HOME/Android/Sdk"
echo "sdk.dir=$ANDROID_HOME" > local.properties
./gradlew :app:assembleDebug
```

The build is offline-capable and reproducible. The artifact **at this tag** is
**2,306,705 bytes**, SHA-256
`4cc90e9aed5bf7170f24f22e9661b307ff68b4bcb922668ba9c99e9ee2e66654`, from two builds of a deleted
output directory that came out byte-identical. **The native helper in it is unchanged and was
re-checked against `app/src/main/jniLibs/` before this release was cut: 18 files, 1,130,556
uncompressed bytes, every path, size and SHA-256 matching.** Every byte of the difference from
alpha.2 is Kotlin.

Then run `grant-storage` in the shell (or tap the hint in the prompt) before `omp`, because
`Documents` needs the all-files grant and without it `omp` creates nothing and says so.

## How to give feedback

This release exists because somebody is installing it on a real phone, so:

1. `adb install -r app-debug.apk`, or `adb install -r app/build/outputs/apk/debug/app-debug.apk`
   if you built it.
2. In the shell, `grant-storage`, and accept the prompt. Without it `omp` will tell you exactly
   that and create nothing.
3. In the shell, **`omp doctor`, and paste the whole thing.** Every line is one `key: value` pair
   in a fixed order precisely so it can be pasted whole and diffed against a second run — if
   something looks wrong, run it again and attach both, because the difference between them is
   usually the interesting part. It is read-only: it downloads nothing, writes nothing, and starts
   and stops nothing.
4. **`omp provision` is the step to try next**, and it is the one thing in this app that has
   never been exercised here at all. It prints what it will cost **before** you type anything, and
   it **moves nothing without a `y` given in that run** — not an empty Enter, not `yes`. On arm64
   it is roughly 334 MiB over the network and about 711 MiB of room on the device. If it is
   cancelled with Ctrl-C, run it again: the partial file's own length is the offset the next run
   asks for.
5. If the app's own chat appears instead of the Debian's, that is a state, not a crash, and the
   `guest origin` section of `omp doctor` names which one it is and why.

**If the app does not open, the logcat settles it, and these three commands are the whole
sequence.** Clear the buffer, start the app by hand, and print the crash:

```bash
adb logcat -c
adb shell am start -n com.omp.terminal/.MainActivity
adb logcat -d AndroidRuntime:E *:S
```

That is how the last round was diagnosed in one message, and it is the fastest thing to send:
three commands and their output say more than anything that can be inferred from a description of
what you saw. If the app opens and something later is wrong, the same buffer with `-d` and no
filter is the thing to send.

**The most useful thing you can send back is `omp doctor` from a phone, before and after a
failure, and the logcat if it dies at all.** Everything else in this repository has been tested
on a JVM; very little of it has been tested on Android, and a phone is currently the only place
that gap can be closed.

## What has never been run

**This statement is weaker than the one in alpha.2, not stronger, and the difference is the
point.** In alpha.2 the honest sentence was that nothing had ever been run on a device. Now
something has: a real Android 14 phone, and it reached the point of dying on launch. **That is
not more coverage, it is a different fact, and it must not be read as though the app now works.**

What has actually been established by the device is narrow and worth stating exactly. **Four
defects on the launch path have now been seen on real hardware** — a missing per-type
foreground-service permission, a scheme stripped off a URL, an uncovered thread body, an
unwrapped guest start — and the app reached none of them successfully. **No path in this project
has run to completion on a device.** The shell has not drawn a line on a phone, the VM has not
booted in an app on a phone, no conversation folder has been opened, no chat has been served,
and the guest has not started. **proot itself has never been executed at all — anywhere,
including in a test — and no `apt` sequence has been run against a real Debian on any ABI, and
no `dpkg` has ever run inside one**, so the figure `omp doctor` reports as dpkg's is a number this
build carries rather than one it has taken.

A helper present in an APK is not a helper that has run. The bytes are verified against the
Termux `.deb` payloads and the layout is verified; whether the kernel will `exec` any of it,
whether the linker resolves what `LD_LIBRARY_PATH` says, and whether an OEM's SELinux policy
permits `ptrace` are all open questions, and one phone that has not got as far as starting
anything has not answered any of them.

**So every claim above about the guest is still a claim about code that has been read and
tested.** The one statement in the whole start path that can only ever run on a phone is
`ProotForegroundServer.launch`'s builder start, and the source marks it as such. Everything above
it — the argument vectors, the environment, the port check, the install sequence and its five
minute bound, the probe, the record, every sentence of every report — is plain JVM and is covered
by tests. `omp doctor`'s closing line says this on the device, and `docs/vm.md` says what a green
report still cannot tell you. **It now has one more thing it cannot tell you, which is that a
green report is not a report from a device that ran.**

The Kotlin half is tested and the tests are real: 816 tests in `:core` and 134 in `:app`, all
green, neither needing a device. They exercise the shell, the VM, the agent, the guest's API
contract, the provisioning layer, the diagnostic, the merged manifest a device actually reads,
and the loopback server over a real socket. **What they still do not exercise is Android, and the
917-test suite that shipped in alpha.2 was exactly that many green tests.**

## One thing that was wrong in alpha.1, and is not now

- **The intermittent `:core:test` failure is fixed, and it was the pipeline's exit status.** It
  appeared once, in seven runs of an otherwise-green suite, and was not seen again in twelve
  further runs at identical per-class counts — so an earlier draft of these notes recorded it as
  unreproduced and unidentified, which was what the evidence of the time supported and no more. It
  was later reproduced deliberately, in a fresh JVM with only `ShellTest` on the classpath: **one
  failure in forty runs**, with the assertion `expected:<1> but was:<0>`. It was then made **100%
  deterministic** by delaying the first stage of a pipeline, and with the old code the wrong
  answers came on every run: `nosuchcmd | true` gave 127 rather than 0, and `cat | false` gave 130
  rather than 1.
  The cause was write authority, not visibility. `Shell.runPipeline` started one thread per stage
  and **every one of them wrote the same `JobGroup.status`**; the watcher joined the last stage and
  then drained the earlier ones for up to two seconds, so any earlier stage returning inside that
  window overwrote the last stage's value, and `$?` was whichever stage happened to write last.
  The fix gives the status to the last stage alone, written before it returns, with the join and
  the latch supplying the ordering — which is why no lock was added, because a lock would have
  hidden the bug rather than removed it. It is gone by count and not by assertion: **five
  consecutive full-suite runs green with the results directory deleted before each, ten of ten
  attempted, plus sixty runs of `ShellTest` in isolation, all green**, against one that failed
  roughly one run in thirty before. `ShellTest` went from 32 tests to 48, and the sixteen added
  are the ones that hold this in place.

## Known not to work, or not to be established

A reader deciding whether to try this needs this list more than the list above. **Nothing in it
has been softened or removed since alpha.1, and two releases since have added to it.**

- **Four launch defects were found by reading the code, not by testing it, and that is not a
  survey.** They were four independent process deaths on one path, found by an audit. There is
  no basis here for saying they were the only four, or that a fifth is not sitting behind the one
  that is fixed. `START_FAILED` and the uncaught-exception handler mean the next one is more
  likely to leave a name in a log than to disappear, and a name in a log is not the same as a
  defect that is not there.
- **The guest's agent is read-only.** The page has an approval dialog and there is an
  `/api/approvals/{id}` route, because this app's own agent puts every write to the user. Three
  runs of the real binary were measured and the guest cannot do it: with nothing asked, the
  `write` tool ran and the file was created; with `--approval-mode always-ask` the question was
  asked on a stream that was at end of input, so every answer read as a decline. The host protocol
  that would fix it is `--mode=rpc`, and **this build establishes nothing about its messages**, so
  it is not used. The guest therefore passes `--approval-mode write`, and
  **`/api/approvals/{id}` answers every id with the app's own 404 sentence.**
- **What a successful `omp update` install prints is unestablished.** The machine this was
  measured on was already current, so "Already up to date" is the only success ever observed here,
  along with the no-network failure. Nothing here reads a line naming a newly installed version,
  and the before-and-after in the record is assembled from two boots' own reports rather than
  invented from one. It must not appear to have watched an update land.
- **The agent's folder boundary is a path check and not a sandbox.** Every path the agent is
  asked about is checked in one class, `omp.agent.tools.Sandbox`, and a symlink's target is what
  is checked. That stops the accident — a model confidently wrong about where it may write, a
  `..` that walked out — and it is not a wall against a determined caller, which in this app would
  be Kotlin inside the app the user already installed.
- **The key is in app-private storage and is not encrypted at rest.** A file under `files/` is
  unreadable by other apps and by a file manager, and that is the whole of the protection:
  anything running as this app's uid — a debuggable build, an `adb backup`, a root shell — reads
  the plaintext. There is no `KeyStore`-backed wrapping of the model key and nothing here claims
  one. **The APK you are about to install is a debuggable build.**
- **There is a port race between the bind check and Apache binding.** The check is a check, not a
  lock: this app closes its socket before Apache is told the number, so another process binding
  the same number in that window — a few milliseconds, and nothing here can close it — is
  possible. The consequence is the safe one: the probe fails, the state is
  `APACHE_NOT_ANSWERING`, and the app's own server is shown *and named as the app's own server*.
- **The guest's LAMP install has never been run against a real Debian, on any ABI.** The sequence
  is three commands — `apt-get update`, `apt-get install -y` on the manifest's four names, and
  `a2enmod php8.4` — and the tests that pin them are a fake launcher and a temporary directory.
  **A fake `apt` is not an `apt`.** Whether `deb.debian.org` is reachable from inside a proot
  guest, whether `mariadb-server`'s `postinst` completes with no init to start a server with, and
  whether these four packages install at all on trixie are all open questions this build refuses to
  answer in advance. The install is bounded at five minutes, stopped rather than left running, and
  its record is written **before** the first step so an app killed here or a phone still doing it
  leaves an answer rather than a silence. **A half-installed stack is `LAMP_FAILED` and never
  presents as a guest that can serve anything**, and on a phone radio that is the ordinary
  outcome of a 55 MB transfer, not the exceptional one. It is a one-time cost, not a per-open
  one: a marker inside the tree is written last and only on a clean run, and a start that finds it
  launches nothing.
- **The LAMP figures are measured for arm64 only.** The other three ABIs carry no figures at all
  and the report says so rather than borrowing arm64's. armhf gets a Debian and **no agent**,
  because upstream ships no 32-bit Linux build of `omp`; x86 gets nothing, because Debian
  publishes no netboot image for i386. Both are refused before a question is asked.
- **Which way the LAMP estimate is wrong is not established, and it is one of the two things only
  a device can say.** `omp doctor`'s `packages:` line puts `dpkg`'s own figure beside the
  manifest's: on a real phone it sums `Installed-Size` over the names this build asked for, reads
  it out of `/var/lib/dpkg/status` **inside the guest's own rootfs** with no guest process and no
  network, and prints it against the estimate. **No `dpkg` has ever run inside a Debian here**, so
  this repository holds no real figure on that side of the comparison — the only such number in it
  is one a test wrote into a status file to exercise the formatting, and a figure invented to
  exercise a formatting is not a measurement of anything. **So no direction of error is claimed
  here, because none has been measured.** The estimate it would be compared against, 376.6 MiB
  (394,945,536 bytes), and the 54.6 MiB (57,211,704 bytes) of download, were measured off-device
  against the Debian trixie arm64 package index on one machine, and `apt` resolving a different
  closure on a device is a real possibility no argument vector can rule out. **The download share
  has no real figure at all** — `apt` deletes the `.deb` files it fetched — so 57,211,704 bytes
  remains an estimate, and the report says so rather than inventing one.
- **The two chat origins cannot be told apart by their content.** A second profile of this app is
  a real case, both serve byte-identical pages, and no content check can separate them. What rules
  it out is the bind check, because a second profile's Apache is *already listening* on the
  reserved number.
- **The token is the whole of the authentication, and it has an edge.** A loopback port is
  reachable by every app on the device, so a request without the token is a `401`. What it is not
  is a defence against a rooted phone or against you: anyone who has the notification, or a
  photograph of it, has the token.
- **A `WebView` renders whatever HTML the page sends**, and the page can come out of a Debian the
  user can `apt install` into. That cannot be mitigated from here. What is bounded is what the page
  can reach: no JavaScript bridge, `file://` and `content://` off, mixed content off, and every
  URL that is not this origin's own scheme, host and port refused, for subresources as well as
  navigations. JavaScript is on, because a chat is JavaScript.
- **The agent's stream has one read timeout, and it is the same one for the response headers.**
  `HttpURLConnection` latches the read timeout onto the socket while parsing the status line, so
  the checkpoint that stops a stalled answer also bounds how long a server has to start answering.
  A chat endpoint that queues and routes to a model can exceed it. Separating the two needs a
  transport with a per-read timeout, and there is no pretending around this one without turning a
  checkpoint into a hang.
- **An agent inside the VM can `vm reset` and throw away the namespace the conversation is in.**
  That is why there is no `run` tool: a line of shell is not something an approval prompt on a
  phone can honestly summarise, so the file tools are here and the shell is not.
- **The agent needs a key before it can say anything, and this build cannot check that a key
  works.** With the all-files grant and no `omp key` yet, a question is refused with the file the
  key would go in. Whether a key that *is* there reaches a working model — a right provider, a
  right endpoint, a reachable one — is not established here, and the failure you get is the
  endpoint's, not a sentence this app wrote about it.

## Where the rest of it is written down

`README.md` is the public face, `docs/vm.md` has the design and the limits of the VM and the
guest in full, and the tests are the specification for anything the two of them leave open.
